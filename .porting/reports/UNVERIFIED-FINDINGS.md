# Unverified audit findings (verify-then-fix pool for batch 5)

From the 2026-08-09 70-agent audit. These were reported by domain reviewers but NOT adversarially
verified (the verify pass covered only each area's top 4). Treat each as a CLAIM: reproduce it
against the 1.18.2 baseline (859f87773) before fixing. Some may be wrong or already-known.

## Recipe types, serializers and codecs

### [low] CrushingRecipe's TierSortingRegistry replacement changes tier ordering and silently degrades unknown tier names to wood
- **File**: src/main/java/com/cannolicatfish/rankine/recipe/CrushingRecipe.java:102
- **1.18.2**: getResults/getAtomizeResults/getPossibleResults/getWeightsByTier all gated on `!TierSortingRegistry.getTiersLowerThan(required).contains(harvestLevel)`, using Forge's global sorted tier list. That list contained WOOD < GOLD < STONE < IRON < DIAMOND < NETHERITE plus every tier any installed mod had registered, and TierSortingRegistry.byName(rl) resolved any of those names from recipe JSON.
- **1.21.1**: `tierQualifies` (line 102-104) is `tierLevel(harvestLevel) >= tierLevel(required)`, over a private TIER_BY_NAME/TIER_LEVELS map (lines 58-75) seeded with only the six vanilla names and with GOLD given level 0, the same as WOOD. `registerTier(...)` (line 62) is the documented extension point but has zero callers anywhere in the mod.
- **Impact**: No effect on shipped content — I checked every rankine:crushing recipe under src/main/resources (192 files) and only minecraft:stone/iron/diamond/netherite appear, and both plain HammerItems (wooden, stone) and every AlloyHammerItem resolve to vanilla Tiers, so all of Rankine's own gating is preserved exactly. Two third-party regressions remain: (1) a datapack recipe with "tier": "minecraft:gold" is now satisfied by a wooden hammer, where 1.18 ranked gold strictly above wood; (2) a recipe naming a modded tier (e.g. "mekanism:osmium") resolved correctly in 1.18 but now falls through tierByName -> null -> Tiers.WOOD with no warning, so that output becomes obtainable with any hammer.
- **Suggested fix**: Give GOLD its own ordinal between WOOD and STONE, and log a warning in Serializer#fromJson when tierByName returns null for a tier string rather than silently substituting Tiers.WOOD, so pack authors see the problem. Optionally call registerTier from commonSetup for any tiers Rankine or its compat partners define.

### [low] AlloyingRecipe's placeholder element id changed from an unresolvable location to a real element (mercury)
- **File**: src/main/java/com/cannolicatfish/rankine/recipe/AlloyingRecipe.java:728
- **1.18.2**: Serializer#fromJson filled the element list with `NonNullList.withSize(t, new ResourceLocation(""))`. That id never resolves through RecipeManager#byKey, so any element slot declared by `total` but missing its `inputN` object stayed inert: getElementList/getIngredientsList skipped it and generateResult could never treat it as an accepted element.
- **1.21.1**: Line 728 uses `NonNullList.withSize(t, ResourceLocation.fromNamespaceAndPath("rankine","elements/mercury"))`. That id DOES resolve, so an unfilled slot now injects the mercury ElementRecipe into getElements(), getElementList(level), getIngredientsList(level) and getIngredientGroupList(level), with mins/maxes defaulting to 0f/0f at that index.
- **Impact**: No shipped recipe is affected — I checked all of src/main/resources/data/rankine/recipe/alloying/*.json and every one declares as many inputN objects as its `total` (the only mismatch, maraging_steel_alloying.json, has one input MORE than total, which 1.18 also ignored). For an add-on datapack that leaves a gap, mercury would appear as a listed element for that alloy in JEI, and worse, if the recipe also legitimately declares mercury at a higher index, `getElements().indexOf(...)` in generateResult (line 421) returns the gap index first and reads min=0/max=0, making the alloy uncraftable. Note the 1.18 network path already padded with rankine:elements/mercury, so the port has merely made the server agree with what 1.18 clients saw.
- **Suggested fix**: Use a deliberately unresolvable placeholder (e.g. ResourceLocation.fromNamespaceAndPath("rankine","empty")) for both the JSON and network defaults, or drop unfilled indices from the list entirely so indexOf can never land on a gap.

## The alloy system: util/alloys, util/colors, util/ElementEquation, items/alloys/*

### [medium] An empty alloy-recipe string is turned into the bogus ResourceLocation "minecraft:" instead of "no recipe"
- **File**: src/main/java/com/cannolicatfish/rankine/items/alloys/IAlloyItem.java:80
- **1.18.2**: 1.18.2 IAlloyItem#createDirectAlloyNBT did `if (alloyRecipe != null) listnbt.putString("recipe", alloyRecipe);` — an empty string was stored as an empty string — and `getAlloyRecipe(stack)` explicitly guarded on it: `if (stack.getTag() != null && !stack.getTag().getCompound("StoredAlloy").getString("recipe").isEmpty()) return new ResourceLocation(...); else return null;`. So "" meant "no recipe" and every downstream null-check worked.
- **1.21.1**: createDirectAlloyNBT line 79-83 does `if (alloyRecipe != null) stack.set(ALLOY_RECIPE, ResourceLocation.parse(alloyRecipe))` with no empty check, and `getAlloyRecipe` (line 165-168) just returns `stack.get(ALLOY_RECIPE)`. `ResourceLocation.parse("")` does NOT throw in 1.21.1 — `withDefaultNamespace("")` -> `assertValidPath("minecraft", "")` and `isValidPath("")` is vacuously true — so it produces a real `minecraft:` ResourceLocation with an empty path. Callers that use "" as the no-recipe sentinel: AlloyIngredientHelper.java:154-159 (`String alloyRecipe = json.has("alloyRecipe") ? ... : ""`) and AlloyCraftingRecipe.java:299 (workingRecipe).
- **Impact**: Any recipe JSON (datapack, addon, or a future rankine recipe) that declares `alloyComp` without `alloyRecipe` produces stacks and ingredients whose ALLOY_RECIPE is `minecraft:` instead of absent. AlloyCraftingRecipe#checkMatch:230-235 then sees a non-null ingredient recipe and demands the player's stack carry the same id, so that crafting recipe can never be satisfied; `generateLangFromRecipe` produces the dead lang key "item.minecraft."; and AlloyPickaxeItem/AlloyArmorItem#isValidRepairItem compare "minecraft:" against the real id and refuse the repair. The four shipped crushing recipes all supply both fields, so this is currently latent in rankine's own data but breaks any datapack that uses only alloyComp.
- **Suggested fix**: Guard the sentinel: `if (alloyRecipe != null && !alloyRecipe.isEmpty()) { stack.set(ALLOY_RECIPE, ResourceLocation.parse(alloyRecipe)); } else { stack.remove(ALLOY_RECIPE); }` in IAlloyItem#createDirectAlloyNBT. Optionally use `ResourceLocation.tryParse` and treat null as "no recipe" so a malformed id degrades instead of throwing.

### [medium] AlloyingRecipe#getResultItem() shows the generic item name in JEI and the machine GUI because getLocalName() needs an id that has not been resolved
- **File**: src/main/java/com/cannolicatfish/rankine/recipe/AlloyingRecipe.java:528
- **1.18.2**: 1.18.2 AlloyingRecipe#getLocalName() built the lang key straight from `this.id`, which the serializer set at datapack load, so `getResultItem()` always applied the `nameOverride` NBT and displayed e.g. "Steel Ingot" wherever the recipe result was shown.
- **1.21.1**: getLocalName() early-returns "" whenever `this.cachedId == null` (line 529). cachedId is only filled by `resolveId(level)`, which runs solely inside `generateResult` (line 376) — and `matches(inv, world, type)` (line 611-613) short-circuits on `cannotMake(...)` before ever calling generateResult. `bindId(...)` (line 88) is never invoked for AlloyingRecipe. So for any recipe the current world session has not actually smelted, getResultItem() (line 626-636) skips the `RankineDataComponents.NAME_OVERRIDE` set.
- **Impact**: Affects the 5 alloying recipes that set `genName: true`. In JEI's alloying category, and in InductionFurnaceContainer.java:109 which calls `recipe.getResultItem(registryAccess()).getDisplayName()` for the GUI's alloy readout, those recipes display the generic fallback name ("Alloy Ingot") instead of their own alloy name until the player has actually run that exact recipe in an alloy furnace, at which point the display silently changes. The crafted item itself is fine because generateResult calls resolveId first.
- **Suggested fix**: Same fix as the Packaged Tool finding: bind ids once on recipe reload — subscribe to RecipesUpdatedEvent (client) / AddReloadListenerEvent or the server's recipe-manager hook, iterate `getAllRecipesFor(RankineRecipeTypes.ALLOYING.get())` and call `holder.value().bindId(holder.id())`. That makes cachedId always available and lets the PORT-TODOs at AlloyingRecipe.java:530 and AlloyCraftingRecipe.java:146 be deleted.

### [low] AlloyIngredientHelper#getItemStack now forces count 1 on the plain-item path when includeCount is false
- **File**: src/main/java/com/cannolicatfish/rankine/recipe/helper/AlloyIngredientHelper.java:119
- **1.18.2**: In 1.18.2 the `includeCount` flag was consulted ONLY inside the `readNBT && json.has("nbt")` branch. The ordinary branch unconditionally did `ItemStack ret = new ItemStack(item, GsonHelper.getAsInt(json, "count", 1));`, so a result declaring `"count": n` kept n even when the caller passed includeCount=false.
- **1.21.1**: Line 119 hoists it: `int count = includeCount ? GsonHelper.getAsInt(json, "count", 1) : 1;` and that single value is used for every branch, so the plain-item path now always produces count 1 when includeCount is false. The two callers that pass false are AlloyingRecipe.java:670 (`getItemStack(object, true, false)`) and CrucibleRecipe.java:312.
- **Impact**: An alloying or crucible recipe whose `result` object carries a `count` greater than 1 now yields/displays a single item where 1.18.2 yielded the declared count. None of the 49 shipped alloying recipes or the crucible recipes declare a result count, so nothing in the base mod changes today; the divergence only bites datapacks and any future recipe that adds one. For alloying specifically the real crafted count is recomputed from input mass in generateResult, so the visible effect there is limited to getResultItem() previews (JEI, furnace GUI).
- **Suggested fix**: Restore the 1.18 asymmetry deliberately, or (better, if the 1.18 behaviour was itself the bug) leave the code as-is and note it in HANDOFF.md's accepted-deltas list. Minimal parity fix: keep `int count = GsonHelper.getAsInt(json, "count", 1);` for the plain-item branch and apply `includeCount ? count : 1` only in the components/NBT branches.

## Items, tools, armor, food, tiers

### [medium] SpearItem and InfusingTotemItem forced-allow overrides moved to the wrong hook, so the enchanting table no longer offers those enchantments
- **File**: src/main/java/com/cannolicatfish/rankine/items/tools/SpearItem.java:191
- **1.18.2**: SpearItem.java:189 overrode `canApplyAtEnchantingTable` to return true unconditionally for IMPALING and LOYALTY, which is the hook `EnchantmentHelper.getAvailableEnchantmentResults` consults — so a Rankine spear could roll Impaling and Loyalty at an enchanting table even though it is not a Trident. InfusingTotemItem.java:93 returned true for every enchantment, so the Totem of Infusing could roll any enchantment at a table (that is the whole point of the item).
- **1.21.1**: Both were ported onto `supportsEnchantment` (SpearItem.java:191, InfusingTotemItem.java:95), which is the anvil hook. The table now goes through the default `isPrimaryItemFor` (IItemExtension.java:453), which after the `supportsEnchantment` check still requires `stack.is(enchantment.definition().primaryItems())` — for Impaling that is `#minecraft:enchantable/trident`, which the repo never populates (see finding 1); for arbitrary enchantments on the totem it is whatever each enchantment declares. Neither class overrides `isPrimaryItemFor`.
- **Impact**: This is the inverse of finding 4: an enchanting table will not offer Impaling or Loyalty on any Rankine spear, and the Totem of Infusing can no longer be table-enchanted with arbitrary enchantments — its 1.18 defining behaviour. Anvil application still works, so the item is half-functional rather than obviously broken.
- **Suggested fix**: Add matching `isPrimaryItemFor` overrides: in SpearItem return true for IMPALING/LOYALTY before delegating to super; in InfusingTotemItem return true unconditionally (matching its `supportsEnchantment`). Keep the existing `supportsEnchantment` overrides so the anvil path is unchanged.

### [low] Alloy Template inventory tint changed from always-white to the dye colour because two differently-cased NBT keys were merged into one data component
- **File**: src/main/java/com/cannolicatfish/rankine/items/AlloyTemplateItem.java:344
- **1.18.2**: `addTemplate` wrote the dye colour under the lowercase key: AlloyTemplateItem.java:164 `stack.getOrCreateTag().putInt("color", dye.getDyeColor().getMaterialColor().col)`. `getColor` (line 339) read the capitalised key: `getTemplate(stack).getInt("Color") == 0 ? 16777215 : getTemplate(stack).getInt("Color")`. CompoundTag keys are case-sensitive, so `getInt("Color")` was always 0 and the template always rendered with the 16777215 no-tint fallback — i.e. dyeing a template never changed its inventory colour.
- **1.21.1**: Both sites now use the same `RankineDataComponents.COLOR` component (write at line 194, read at line 345), so `TemplateItemColor` (util/colors/TemplateItemColor.java) returns the real dye colour. The delta is acknowledged in a code comment at AlloyTemplateItem.java:341-343 but not in HANDOFF.md or CHANGELOG.md.
- **Impact**: Alloy Templates now render tinted by the dye used to make them instead of the plain white they had in 1.3.8. Cosmetic only, and arguably what the original author intended — but it is a visible change to an existing item and a 1.18 world's templates will change appearance on load.
- **Suggested fix**: Low priority. Either keep it and promote the code comment into HANDOFF.md's accepted-deltas list so it is a reviewed decision, or restore parity by having `getColor` return 16777215 unconditionally with a comment explaining the 1.18 key mismatch.

## Enchantments

### [medium] Prying and Puncture now trigger on ranged/indirect damage and no longer read off-hand or armour slots
- **File**: src/main/java/com/cannolicatfish/rankine/events/handlers/common/LivingDamageHandler.java:173
- **1.18.2**: `PryingEnchantment#doPostAttack` and `PunctureEnchantment#doPostAttack` were invoked only by `EnchantmentHelper.doPostDamageEffects(attacker, target)`, which vanilla calls from `Player#attack` and `LivingEntity#doHurtTarget` after a *melee* hit landed. That helper iterates the attacker's `getAllSlots()` (both hands plus all four armour slots), so a Prying crowbar in the off-hand also fired.
- **1.21.1**: `onPostDamage(LivingDamageEvent.Post)` fires for every damage instance whose `getSource().getEntity()` is a LivingEntity, with no check that the damage was a direct melee attack, and reads only `attacker.getMainHandItem()` (lines 174-189). `LivingDamageEvent.Post` is posted from `LivingEntity#actuallyHurt` for all damage types, including projectiles, thrown spears, blunderbuss cannonballs, and any indirect source that carries an owner.
- **Impact**: A player holding a Prying crowbar in the main hand who kills a mob with a bow, blunderbuss, thrown spear or ender ball now disarms it — 1.18 required a melee swing. Conversely, Prying/Puncture on an off-hand crowbar/spear no longer does anything, where 1.18 fired it.
- **Suggested fix**: Gate `onPostDamage` on a direct melee attack (e.g. `!event.getSource().isIndirect()` / `event.getSource().getDirectEntity() == attacker`), and iterate the attacker's equipment (`attacker.getAllSlots()` or at least main + off hand) rather than only the main hand, to match `EnchantmentHelper.doPostDamageEffects`.

### [medium] Endolithic's "stone" test narrowed from Material.STONE to three base-stone tags
- **File**: src/main/java/com/cannolicatfish/rankine/items/alloys/AlloyShovelItem.java:77
- **1.18.2**: `AlloyShovelItem.useOn` gated the Endolithic teleport on `blockstate.getMaterial().equals(Material.STONE)` (859f87773:.../AlloyShovelItem.java:89 and :118). In 1.18.2 `Material.STONE` is the catch-all rock material: stone and all its variants, cobblestone, all stone/deepslate/blackstone bricks, every ore, netherrack, obsidian, bedrock, and stone-like functional blocks (furnace, dispenser, …).
- **1.21.1**: `isStoneLike(BlockState)` = `state.is(BlockTags.BASE_STONE_OVERWORLD) || state.is(BlockTags.BASE_STONE_NETHER) || state.is(Tags.Blocks.STONES)` — natural, unprocessed base stone only (stone/granite/diorite/andesite/tuff/deepslate, netherrack/basalt/blackstone).
- **Impact**: Right-clicking cobblestone, stone bricks, any ore, obsidian or a mined-out wall with an Endolithic ender-amalgam shovel no longer teleports the player to the surface. In practice the enchantment only works against untouched worldgen stone, which is a large silent nerf to an end-game enchantment.
- **Suggested fix**: Introduce a dedicated block tag (e.g. `rankine:endolithic_teleportable`) populated to approximate 1.18's `Material.STONE` — at minimum `#minecraft:base_stone_overworld`, `#minecraft:base_stone_nether`, `#c:stones`, `#c:cobblestones`, `#c:ores`, `#minecraft:stone_bricks`, deepslate/blackstone/tuff bricks, obsidian — and test against that instead.

### [low] `rankine:enchantable/*` tags enumerate only Rankine + vanilla items, so cross-mod applicability is lost
- **File**: src/main/java/com/cannolicatfish/rankine/data/RankineItemTagsProvider.java:108
- **1.18.2**: `RankineEnchantmentTypes` built its categories from `instanceof` predicates evaluated at runtime: `MINING` = `itemIn instanceof ShovelItem || itemIn instanceof PickaxeItem`, `PEWTER`/`ALLOYTOOL` = `itemIn instanceof IAlloyTool`, `HOE` = `itemIn instanceof HoeItem`. Any other mod's pickaxe, shovel or hoe therefore accepted Quake, and every future Rankine tool was covered automatically.

- **Impact**: Quake can no longer be applied to a pickaxe or shovel from any other mod, where 1.18 allowed it. Also a maintenance hazard: any tool added later must be manually added to the tag or its enchantments silently stop working.
- **Suggested fix**: Add `#c:mining_tools` / `#c:tools/pickaxe` + `#c:tools/shovel` (and `#minecraft:enchantable/mining`) as `addOptionalTag` entries to `rankine:enchantable/mining`, and similarly widen the other tags with the closest common tags, so third-party items are picked up the way the old `instanceof` predicates did.

## Event handlers — src/main/java/com/cannolicatfish/rankine/events/

### [medium] Prying/Puncture now trigger on any damage with a living source, not just melee attacks, and no longer see off-hand or armor copies
- **File**: src/main/java/com/cannolicatfish/rankine/events/handlers/common/LivingDamageHandler.java:173
- **1.18.2**: PryingEnchantment.doPostAttack / PunctureEnchantment.doPostAttack (859f87773 enchantment/PryingEnchantment.java, enchantment/PunctureEnchantment.java) were invoked by vanilla's EnchantmentHelper#doPostDamageEffects, which is called only from `Player#attack` and `Mob#doHurtTarget`, and only inside the `if (flag)` branch after `target.hurt(...)` returned true — i.e. successful melee hits only. That helper iterated the attacker's whole equipment set (getAllSlots), so an enchanted crowbar/spear in the off-hand or an armour slot also fired.
- **1.21.1**: LivingDamageHandler.onPostDamage subscribes to LivingDamageEvent.Post (RankineEventHandler.java:149-153), which NeoForge fires from LivingEntity#actuallyHurt at net/minecraft/world/entity/LivingEntity.java:1759 for EVERY damage application. The only gate is `event.getSource().getEntity() instanceof LivingEntity attacker` (line 174) and the level is read only from `attacker.getMainHandItem()` (line 177).
- **Impact**: Puncture's bonus magic damage and Prying's disarm roll can now fire on damage that is not a melee attack at all — arrows/projectiles/explosions/indirect damage attributed to the attacker while the enchanted item happens to be in main hand — and on mob-dealt damage where the mob is holding an enchanted item. Conversely, Prying/Puncture carried in the off-hand or on armour no longer fire at all. It also runs mid-hurt() (before the outer knockback/death handling), so applyPuncture's nested `ent.hurt(magic, ...)` re-enters hurt() before the original hit finishes resolving, which can flip the order in which the kill is attributed.
- **Suggested fix**: Gate onPostDamage on the source actually being a direct melee attack — e.g. `event.getSource().getDirectEntity() == attacker && !event.getSource().is(DamageTypeTags.IS_PROJECTILE) && !event.getSource().is(DamageTypeTags.IS_EXPLOSION)` — and iterate the attacker's equipment slots (main hand, off hand, armour) the way EnchantmentHelper#doPostDamageEffects did, rather than main hand only.

### [low] Repulsion/Mercury retarget now cancels the target change (mob keeps its old target) instead of clearing it
- **File**: src/main/java/com/cannolicatfish/rankine/events/handlers/common/LivingSetAttackTargetHandler.java:18
- **1.18.2**: LivingSetAttackTargetHandler.java (859f87773) reacted to LivingSetAttackTargetEvent, which fired AFTER the target was assigned, and forced `((Mob) event.getEntityLiving()).setTarget(null)` — clearing the mob's aggro completely.
- **1.21.1**: The port maps to LivingChangeTargetEvent (fired pre-assignment from Mob#setTarget, net/minecraft/world/entity/Mob.java:242-246) and calls `event.setCanceled(true)`. Per the event's own javadoc (net/neoforged/neoforge/event/entity/living/LivingChangeTargetEvent.java:31): 'If you cancel this event, the target will not be changed and it will stay the same.' Mob.java:244 confirms `this.target` is left untouched on cancel.

### [low] Stone brick slabs, stairs, walls and pressure plates were promoted from solid to cutout, losing mipmapping
- **File**: src/main/java/com/cannolicatfish/rankine/data/RankineBlockStateProvider.java:734
- **1.18.2**: 859f87773:.../init/ClientProxy.java filtered each stone group with `if (blk instanceof RankineStoneBricksBlock) blockList.add(blk);` before calling addCutout. In 859f87773:.../blocks/block_groups/RankineStone.java only two fields per stone are that type — `RegistryObject<RankineStoneBricksBlock> bricks` and `mossyBricks` (lines 26-27, 71-72). getBricksSlab/getBricksStairs/getBricksWall/getBricksPressurePlate return plain SlabBlock/StairBlock/WallBlock/PressurePlateBlock, so they failed the instanceof test and stayed on the solid layer.
- **1.21.1**: Lines 732-740 add all nine per stone to the cutout list: getBricks, getMossyBricks, getBricksSlab, getMossyBricksSlab, getBricksStairs, getMossyBricksStairs, getBricksWall, getMossyBricksWall, getBricksPressurePlate. ### [low] Boat bubble-column wobble no longer scales the model, diverging from both 1.18.2 and vanilla 1.21
- **File**: src/main/java/com/cannolicatfish/rankine/client/renders/RankineBoatRenderer.java:89
- **1.18.2**: 859f87773:.../client/renders/RankineBoatRenderer.java did `p_113932_.mulPose(new Quaternion(new Vector3f(1.0F, 0.0F, 1.0F), p_113929_.getBubbleAngle(p_113931_), true));`. The old Mojang Quaternion(Vector3f, angle, degrees) constructor multiplies the raw axis components by sin(theta/2) without normalising, so for the axis (1,0,1) the quaternion has magnitude^2 = 1 + sin^2(theta/2) > 1, and applying it through the pose matrix scales the model as well as rotating it. Vanilla 1.21.1 deliberately preserves this: BoatRenderer.java:76 uses `new Quaternionf().setAngleAxis(angleRad, 1.0F, 0.0F, 1.0F)`, and JOML's setAngleAxis also skips normalisation.
